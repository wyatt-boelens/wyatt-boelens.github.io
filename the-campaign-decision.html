CASE STUDY — SYSTEMS DESIGN

The Campaign Decision

A layer that sits on top of the Buying Committee Router. Before running it, this decides whether a prospect just needs one message — the Router's normal job — or a longer campaign spread across several messages over days or weeks. Built so the extra planning only happens when a deal actually calls for it.

Genericized reconstruction for portfolio purposes. The architecture below is real and mine. The company and brand names are fictional.

The problem

Not every prospect deserves the same amount of effort. A well-researched, multi-message campaign makes sense for a short list of high-value accounts. It's overkill for a routine list of fifty — and if the system always defaults to the heavier version, it gets slow enough that people stop using it and just go back to doing things by hand.

  • Always running the full version wastes time on prospects that didn't need it.
  • Always running the fast version misses real opportunities that deserved more effort.

This exists to make that choice explicit every single time, instead of drifting toward whichever option is the default. That's what keeps quick lists quick and real campaigns getting real depth — without extra headcount to manage two separate processes by hand.

The architecture
01
Every batch starts with the same question, asked out loud

Before anything happens, the system asks: one message, or a real campaign? It never assumes based on list size — asking every time is what keeps the fast option from quietly disappearing.

02
What to say and how to say it are decided separately

What the message is about uses the same role logic as the Buying Committee Router. How it's delivered — formality, follow-up frequency — is a separate decision. Keeping these apart means message content never needs rebuilding just because delivery style changes.

03
Two different reasons to mention another company, kept separate

One kind of reference answers "why would this make sense for you." A different kind answers "why now" — a direct competitor already doing this, which carries real risk if handled carelessly. That second kind stays vague and safe by default, specific only with direct approval.

04
The same mistake never goes out twice to the same account

An early test caught two people at one company getting the exact same message. Fixed two ways: the wording rotates between options, and timing is staggered so two contacts at one company never get the same message the same day.

05
Timing comes from a proven playbook, not a fresh guess every time

A small set of tested timing patterns, chosen by list size and account size, not researched from scratch each run. Every pattern is realistic for one person to actually execute — not a team-sized plan nobody could run alone.

Extend or rebuild — the trade-off, considered before committing

Before building this, the real question wasn't whether it was possible — it was whether it would actually make things better, or just look more impressive without being more useful day to day. Weighed honestly against the simpler version that came before:

  • Speed on a routine batch — unchanged. A normal list still runs just as fast, since the fast option stays available on purpose.
  • Personalization depth — clearly better. A real multi-touch campaign, when one's warranted, goes deeper than a single message ever could.
  • Consistency — slightly worse. More moving parts means more room for something to get applied differently from one campaign to the next.
  • Usability of the output — better. Output is grouped for direct use now, not a raw table someone has to reformat first.
  • Relationship risk — worse, but managed. Referencing another company's status carries real risk if handled carelessly — the system defaults to caution, but the exposure is real in a way the simpler version didn't have.
  • Maintenance — worse. More logic, more pieces, more that can eventually need updating.

Not every measure moved in the right direction. What made it worth building anyway was making sure the fast, simple option never actually disappeared — that's what kept this a real upgrade instead of just a more complicated version of the same tool.

Why this matters

Most people evaluate a new system by what it can do. Fewer check what happens to the thing it's replacing — whether it quietly stops getting used because it got too complicated. Checking that trade-off before building, not after, is what kept this from becoming a more powerful tool that actually gets opened less.

Where this stops

This decides effort level and handles timing — it doesn't decide who to target or write the message itself. That's the Buying Committee Router's job, used underneath this system every time, whether the answer is one message or twenty.
